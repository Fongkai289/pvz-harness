## 模块分工

| 模块 | 职责 |
|---|---|
| Windows 客户端 | 截图、执行已授权输入、只读裁判状态、控制台；菜单由操作员控制 |
| Qwen 识图 | 资源/卡片、植物矩阵、僵尸观察；代码辅助识别卡片、草坪、铲子与位置 |
| Planner | 提供目标、优先级、预算建议、威胁和有效期；不直接点击 |
| Jev | 在文字候选中选择动作或等待，不接收图片 |
| System0 | 版本化玩家模块；生成上下文、选项和动作；经过闸门的 reflex/fallback 由配置控制 |
| Coach / Engineer | 复盘、提出可测目标、修改策略或受限玩家代码并请求评测 |
| 固定裁判与门槛 | 根据胜负、小推车触发时间等评测；玩家模块不能修改评分与权限边界 |

模型权重不更新。这里的 RSI 指候选代码/策略的评测与晋升，不等于传统强化学习的梯度训练。

## 两条游戏链路

真实游戏采用 GOTY 1.2.0.1096：实时截图和真实鼠标输入，受模型延时影响；内存只读且仅供裁判/标注/复盘。
Portable 是独立游戏实例：读取受限 game state 或渲染图，模型等待时暂停游戏时钟，动作通过私有 Harness 协议执行。
两者环境不同，训练结果不能直接等同实战结果。Portable 的五处上游修改、Harness.cpp 和构建/基准工具现已在 `third_party/pvz-portable/` 以固定版本补丁保存。

## 训练与晋升

当前按关卡训练模式每关维护自己的策略，失败或使用小推车时可同时产生 A/B 两个尝试，修改后重打该关种子，按 `level-v1` 门槛选择改进。
这是较快但证据较弱的单关开发循环。旧的多种子、留出集和像素审核模式仍是独立研究入口，不应把两种评测标准混为一谈。
策略文本、调用节奏和 System0 模块可改；接口、操作权限、资源限制、裁判及晋升规则由 harness 控制。
`data/CURRENT` 与 `levels.json` 指向实际使用版本；文档不再写死“当前永远是 v010”。

## 配置、目录与发布

- 主仓库放 `app/`，外部引擎/工具放并列的 `external/`。详见 [workspace-layout.md](workspace-layout.md)。
- `local.example.json` 可提交；真实 SSH 入口写在不提交的 `local.json`，统一由配置模块读取。
- `.env` 位于服务器，保存令牌和模型配置；Jev 需要明确设置 `PVZ_JEV_MODEL_DIR`。
- Codex Coach 是可选配置；默认可使用 Qwen Coach，不要求每个使用者都有 Codex。
- 游戏截图/裁剪模板从当前公开树移除，本机保留；生成方法见 [assets.md](assets.md)。
- 原创代码 MIT；Portable、Emulator、AutoTrust 等许可证独立，见 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)。
- GitHub Actions 运行不依赖私有游戏素材或模型服务的 Linux 测试，并重建补丁后的上游源码。

## 与专门训练的游戏智能体的区别

本项目使用通用模型推理和代码/策略搜索，无法把“每次游戏调用大模型”的吞吐等同于专用小网络的大规模自博弈训练。
主要限制是推理开销、开发种子过拟合、训练与实战观察差异，以及尚无充分的跨种子/跨关卡评测曲线。
已经完成闭环，不代表闭环已能持续、稳定提升；后续应以固定基线、留出种子、重复运行和实战验证衡量。
